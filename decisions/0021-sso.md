# 0021: Single sign-on (OIDC) without giving up zero knowledge

Status: Accepted by the operator on 2026-11-08; option 1 built 2026-11-25
Date: 2026-11-08
Backlog: B8

## Context

Organizations want people to sign in with their company identity (Microsoft Entra ID, Google
Workspace, Okta, Keycloak) and want offboarding to happen in one place. Today a sign-in proves
the master password, which also derives the key that opens the vault. An identity provider can
prove *who* someone is, but it cannot hand Vault a key it never had.

## Options

1. **SSO for sign-in, the master password still unlocks.** (1Password's model before
   "unlock with SSO", and Bitwarden's default.)
   - OIDC replaces the email-and-password *authentication* step and enforces the provider's
     MFA, account status and offboarding.
   - After it, the browser still asks for the master password to unwrap the vault key.
   - The zero-knowledge model is unchanged; people keep one extra secret.
2. **Trusted devices** (Bitwarden "trusted device encryption", 1Password "unlock with SSO").
   - A device enrolled once, with the master password or an admin's approval, keeps a
     device key in the browser and unlocks after an SSO sign-in with no master password.
   - Recovery goes through an admin-approval key (a key escrowed to org admins).
   - It is convenient, but **admins can then reach members' vault keys** by design, which
     must be stated plainly.
3. **Key Connector** (Bitwarden): the operator runs a separate service that holds users' keys
   and releases them after SSO. That is not zero knowledge with respect to the operator.

## Recommendation

**Option 1 first**, behind `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`:

- PKCE authorization code flow, with the server as the OIDC client.
- Accounts are matched by verified email (the digest only, as today).
- **Required for an organization's members when its policy says so.** Disabling the account at
  the provider stops the next sign-in, and the allow-list (G2) and session length (G1) still apply.
- Registration can be *provisioned on first SSO sign-in* when the operator allows it, with
  invite-only kept as the default.

Option 2 stays a possible later step. It needs its own decision, because it changes who can
open a vault.

## Consequences (if accepted)

- One new external dependency per installation: the operator's identity provider. No paid
  service is involved; Keycloak or Authentik cost nothing to self-host.
- New threats: a compromised identity provider can sign someone in, but cannot open their vault
  under option 1. ID token validation (issuer, audience, nonce, signature by the provider's
  JWKS) must be tested against a real provider, which is a CI job with Keycloak in a container.

## As built (option 1)

**Configuration.** `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, plus:
- `OIDC_NAME`, the button's label;
- `OIDC_PROVISION`, off by default;
- `OIDC_REQUIRE_VERIFIED_EMAIL`, on by default (off for Entra ID).

The redirect URI is `https://<address>/api/auth/sso/callback`. See docs/configuration.md.

**The flow:**
1. **`GET /api/auth/sso/start`.** The server stores state, nonce and a PKCE verifier for 10
   minutes, as hashes and single use, and redirects to the provider with
   `scope=openid email profile` and `S256`.
2. **`GET /api/auth/sso/callback`:**
   - The code is exchanged at the token endpoint, with `client_secret_basic`, or
     `client_secret_post` if that is all the provider offers.
   - The ID token's signature is checked against the provider's JWKS: RS256, ES256 or PS256.
     HS256 and `none` are refused, and keys are refetched once on an unknown `kid`.
   - Also checked: `iss`, `aud`, `azp` when there are several audiences, `exp` and `iat` with
     60 s skew, `nonce`, and `email_verified`.
   - The browser is sent to `/app/#sso=<ticket>`. The ticket is random, single use, lives
     five minutes and is stored as a hash. A fragment never reaches a server or a Referer.
     Failures come back as `#sso-error=<code>`, which the app explains.
3. **`POST /api/auth/sso/ticket`** says which account the ticket is for.
4. **`POST /api/auth/login`** with the master password **and** `ssoTicket`. The ticket must be
   for that account, and is used up only once the second factor, if any, is in. Vault's own
   two-factor still applies.

**Require single sign-on** is a server policy (console → Policies), offered only when a provider
is configured. Without a ticket for the account, password, recovery-key and passkey sign-ins
are refused with `sso_required`. **Owners are exempt**, so a broken provider cannot lock everyone
out. The sign-in screen then offers only the provider, with a folded "Server owner?" link.

**Provisioning** (`OIDC_PROVISION=true`): a ticket for an address with no account lets that
address, and only that one, register without an invitation. The person still chooses a master
password and gets a recovery key.

**Rate limits.** Start and ticket reads have their own per-address limit (30 per 15 minutes).
The sign-in that follows counts against the usual sign-in limit.

**Activity.** Records `sso-login`.

**Not in this stage:**
- the browser extension through the provider: with SSO required, only owners sign in there;
- a provider per organization, for tenants on the hosted edition;
- option 2 (trusted devices), which needs its own decision.

**Tests:**
- **API**, against an in-process provider:
  - every ID-token check, each with its own spoiled token;
  - PKCE and client authentication;
  - state and ticket reuse and expiry, and tickets bound to their account;
  - the requirement on all three sign-in paths, and the owner exemption;
  - provisioning.
- **e2e**, the same in the browser.
- **CI job `sso`**: the flow through a real Keycloak 26 login page (`tests/keycloak/`).
