Security

How Vault keeps your secrets

The design assumes the entire server side is hostile. This page explains what that means in practice, what is encrypted and how, and — just as plainly — what it does not protect against.

The model

Vault is a zero-knowledge password manager. Encryption and decryption happen only in your browser. The server stores what it is given and checks who is asking, but it never holds a key that can open a vault, and it never sees the master password.

The test the design is held to: if an attacker took a full copy of the server — its disk, its database, its backups, its configuration — they should get ciphertext and nothing more.

Keys

Everything starts from your master password and a random salt unique to your account.

Master password + salt │ PBKDF2-SHA256, 600,000 rounds ← in your browser ▼ Master key ──┬── HKDF "kek" ──► Key-encryption key ──► unlocks the vault key └── HKDF "auth" ──► Login key ──► sent to the server Vault key (random, created once at sign-up) ├── locked by the key-encryption key (master password path) ├── locked by the recovery key (recovery path) └── encrypts every entry, AES-256-GCM
  • The login key and the key-encryption key are separate branches. Knowing the login key tells you nothing about the key that opens the vault, so the one thing the server receives is useless for decryption.
  • The server stores a scrypt hash of the login key, not the key itself.
  • A random vault key sits in the middle. Changing your master password re-locks that one key; your entries are never re-encrypted.

Every write uses a fresh 96-bit nonce, and each entry's ciphertext is bound to its own ID, so an entry cannot be swapped into another's place without detection.

Signing in

Your browser first asks for your account's salt. An email with no account receives a convincing decoy salt, so the sign-in form cannot be used to discover who has an account.

Your browser then derives the keys, sends only the login key, and receives back your locked vault key, which it unlocks itself. A wrong password fails on the server's check; a damaged key would fail in your browser — either way, the server never learns your password.

Repeated failures are rate-limited per address and per account.

Recovery

At sign-up your browser creates a recovery key and shows it to you once. It is never sent to the server. A second copy of your vault key is locked with it, which is the only way back in if you forget the master password.

There is no password reset and no support override, because there is nothing the server could reset. If both the master password and the recovery key are lost, the vault cannot be opened.

What the operator can see

Whoever runs this Vault has an admin panel. It exists to manage accounts, not to look inside them, and it is limited by the same design as everything else: the server holds nothing readable to show.

The admin panel canIt cannot
See that an account exists, when it was created and last signed inSee its email address — only a keyed hash is stored
See how many items an account holdsSee what any item is, or its name
Open or close registration, and issue single-use invitationsReset a master password or unlock a vault
Sign an account out everywhere, disable it, or delete itRead, change or export anyone's entries

Admin access comes in four roles. The owner is set in the server's configuration and can do everything; owners grant the others. Admins manage accounts and invitations, marketing edits this website's text and images, and viewers can look without changing anything. None of the roles can read a vault.

Website editing is limited to plain text, links and uploaded photos. Everything typed is shown as text, never run as code, because this site shares its address with the app that handles master passwords. This page itself cannot be edited from the panel, so what it says always matches how the system works.

Every admin action is written to an audit log before it runs. Admin access is a normal sign-in — there is no separate master key or back door.

In the browser

  • Keys stay in memory. Nothing sensitive is written to local storage, session storage, IndexedDB, or cookies. Reloading or closing the tab locks the vault, and fifteen idle minutes lock it automatically.
  • A strict Content-Security-Policy. No inline scripts, no eval, and network access limited to this server. Injected code cannot quietly send data somewhere else.
  • No third parties. No analytics, fonts, CDNs, or icon services. Fetching a website's icon would reveal which sites you use, so Vault never does.
  • A small dependency tree. The cryptography package has no third-party dependencies at all and is tested against published standard vectors.

Infrastructure

  • HTTPS only, with HSTS. TLS 1.0 and 1.1 are refused.
  • The API listens on the loopback interface only; it is reachable solely through the web server in front of it.
  • The server has no SSH access open to the internet. New releases are pulled by the server from private storage and checked against a hash before they are installed, so deploying needs no way in.
  • The database lives on a private network, not on the web server's disk.
  • Encrypted exports are taken daily to private object storage. Restoring them has been tested. They contain the same ciphertext as the database and nothing more.

Known limitations

A security page that lists only strengths is a marketing page. These are the risks that are known and currently accepted.

The web address is the trust anchor

Any web-based password manager is only as trustworthy as the code it is served. Whoever controls this site's address could serve modified code that captures a master password as it is typed — and that would bypass everything above.

Today the address is a free dynamic-DNS name, which places that control with a third-party service. Moving to a registered domain is planned. Until then, this is the largest risk, and it is accepted knowingly rather than hidden.

One server

The service runs on a single host. If it goes down, the vault is unavailable until it is restored — but your data is in the database and the daily exports, not on that host.

Your own device

Malware on your computer, or a malicious browser extension, can read what you type and what the page shows. No web application can defend against a compromised device.
